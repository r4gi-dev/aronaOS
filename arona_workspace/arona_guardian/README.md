# arona_guardian

AronaOS Guardian(免疫系)の骨組み実装。

実装計画(設計まとめドキュメント「27. 具体的な実装計画」)の順序3に対応する。
決定論的なルールベースの監視システムで、思考コアの熟慮を経ずに危険な処理を
即座にブロックする(設計まとめ 3〜4章)。

## 構成

| ファイル | 役割 |
|---|---|
| `src/schema.rs` | 脅威カテゴリ(`ThreatCategory`)・検知方式(`DetectionMethod`)・ルール(`GuardianRule`)・システムイベント(`SystemEvent`)のスキーマ |
| `src/engine.rs` | ルールエンジン本体。ルールの追加・緩和・誤発動対応・イベント評価 |
| `src/audit.rs` | 介入記録を`arona_memory`のアロナ記憶へ監査ログとして書き込む連携 |

## 設計まとめドキュメントとの対応

- **進化型ガバナンス**: 新規ルールは`add_rule()`で即座に本番反映される(設計まとめ 4章)
- **非対称セーフガード(聖域)**: `protected`フラグが立ったルールは`relax_rule()`で
  拒否され、`GuardianError::ProtectedRule`を返す。不可逆な損害(ランサムウェアの
  暗号化・データ完全消失)に関わる初期ルールは`protected: true`で登録している
- **誤発動対応**: `record_false_positive()`が一定回数(`FALSE_POSITIVE_AUTO_RELAX_THRESHOLD`)
  を超えると、非保護ルールに限り自動で緩和する(設計まとめ 4章)
- **介入は「止める」のみ**: `InterventionAction`は`Block`のみを持ち、是正処置は
  意図的に実装していない(思考コアに判断を委ねる設計)
- **監査性・透明性**: `audit::log_intervention()`が全ての介入をアロナ記憶に書き込む。
  想起しやすさの重要度を高めに設定し、時間が経っても振り返りやすくしている
- **4種類の検知方式**(設計まとめ 19章): `DetectionMethod`にシグネチャー・挙動・
  しきい値・チェックサム・イベントログ・異常プロセス・ハートビートの7種類を用意し、
  4つの脅威カテゴリそれぞれに対応させている

## 現時点でスタブになっている部分(今後の課題)

- `SystemEvent`は実際のカーネル・OS APIからのフックではなく抽象表現。カーネル統合時に
  実イベントへの置き換えが必要(実装計画 27章の想定通り)
- センサー値の実取得(SMART情報・CPU温度など)は未実装。`SensorReading`イベントを
  誰が・どうやって発行するかは、実際のハードウェアアクセス層の実装待ち
- 思考コアからの新規ルール提案・誤発動判定の自動フィードバックループ(`arona_cognition`
  との接続)は未実装。現状は`GuardianRule::new_proposed()`を手動で呼び出す形
- Guardianの最高優先度スケジューリング(設計まとめ 18章)は、実際のカーネルが
  存在しないフェーズ1では実現しようがなく、将来のカーネル統合時の課題
